# Research: rustybuzz Shaping On Native Hosts And wasm32

**Status**: Finding recorded
**Date**: 2026-11-22
**Card**: [flyingrobots/geordi#137](https://github.com/flyingrobots/geordi/issues/137)
**Feeds**: [flyingrobots/geordi#142](https://github.com/flyingrobots/geordi/issues/142)
(use `rustybuzz`, or keep advance-only layout for profile 1), under the render law of
[flyingrobots/geordi#78](https://github.com/flyingrobots/geordi/issues/78)

This record answers one question with evidence. It does not choose the shaper; #142 does.

## Question

Does `rustybuzz` give identical shaping output on native x86_64, native aarch64 and wasm32 for
Latin text with the pinned Lato face?

## Answer

**Yes, for these inputs on these hosts.** All 344,015 output values (glyph ids, clusters,
`unsafe_to_break` flags, advances and offsets for 200 strings under five configurations) were
identical on aarch64 macOS, AMD x86-64 Linux, and wasm32 in Node and headless Chromium, in every
build listed below. The source review found no float arithmetic on the way to an output value
for this face. This is a finding about these inputs, builds, hosts and one face. It does not prove
that `rustybuzz` never diverges; see [Limits](#limits).

## Method

The experiment is [`research/rustybuzz-wasm32/`](../../research/rustybuzz-wasm32/), a crate outside
the Cargo workspace. It has its own empty `[workspace]` table and `Cargo.lock`, so `rustybuzz` is not
a workspace dependency.

- The face is the repository's pinned
  [`Lato-Regular.ttf`](../../fixtures/render-everywhere/assets/fonts/lato/Lato-Regular.ttf), sha256
  `d636e4683231f931eda222d588e944d082bfd3bdba02f928bee461c0f185b251`, embedded with
  `include_bytes!`. It is the only Lato face in the repository. Nothing was downloaded. It is a
  static TrueType font with `GSUB`, `GPOS` and `glyf` tables and no `GDEF`, `kern`, `fvar`, `gvar`,
  `COLR`, `sbix` or `CBDT`.
- `src/lib.rs` holds 200 strings: 72 written by hand and 128 generated by an integer-only PRNG
  (splitmix64) from a 64-character alphabet weighted towards kerning and ligature letters, with
  precomposed and combining marks. Each string is shaped under five configurations:

  | Configuration | Direction | Features | Language | Cluster level |
  | --- | --- | --- | --- | --- |
  | `ltr-default` | left to right | defaults | `en` | monotone graphemes |
  | `ltr-no-kern-no-liga-characters` | left to right | `-kern,-liga,-clig` | `en` | characters |
  | `ltr-optional-features-turkish` | left to right | `+dlig,+smcp,+c2sc,+onum,+pnum,+tnum,+frac,+case,+sups,+subs,+ss01,+salt,+zero` | `tr` | monotone characters |
  | `rtl-forced` | right to left | defaults | `en` | monotone graphemes |
  | `vertical` | top to bottom | defaults | `en` | monotone graphemes |

  The last two are outside the card's aperture. They reach more of the shaper; vertical
  positioning asks for glyph extents and vertical origins, which horizontal text never does.
- Every glyph's id, cluster, `unsafe_to_break` flag, x and y advance and x and y offset are written
  as 32-bit words: 1,000 runs, 49,145 glyphs, 344,015 values.
- The native binary prints the stream as hex in one JSON line. `--glyphs` prints one JSON line per
  shaped string instead, for reading. The `cdylib` built for `wasm32-unknown-unknown` exports
  `dump_ptr` and `dump_len` and has no imports, so the same `.wasm` file runs in Node and in a
  browser page unchanged.
- [`run.mjs`](../../research/rustybuzz-wasm32/run.mjs) builds each variant, runs it, and compares
  every word with the native release build of the same run. A mismatch is reported with
  configuration, string, glyph, field and both values. Every variant is also compared with the
  per-run SHA-256 values in [`golden.json`](../../research/rustybuzz-wasm32/golden.json), recorded on
  aarch64-apple-darwin, which gives the cross-host comparison.
- `pnpm test` runs `pnpm test:research:rustybuzz-wasm32`, which also runs `cargo fmt --check`,
  clippy with `-D warnings` and the crate's tests. The tests check that Lato kerns `AV` and ligates
  `office`. Under `CI=true` a variant that cannot build or run fails the run.

Re-run it with:

```sh
pnpm test:research:rustybuzz-wasm32
cargo run --release --manifest-path research/rustybuzz-wasm32/Cargo.toml -- --glyphs
```

### What the inputs reach

From the `coverage` line of the reference build:

| Configuration | Glyphs | Runs with fewer glyphs than code points | Runs with a nonzero offset | `.notdef` glyphs |
| --- | --- | --- | --- | --- |
| `ltr-default` | 9,768 | 114 | 103 | 11 |
| `ltr-no-kern-no-liga-characters` | 9,866 | 90 | 103 | 11 |
| `ltr-optional-features-turkish` | 9,866 | 90 | 59 | 11 |
| `rtl-forced` | 9,779 | 109 | 106 | 11 |
| `vertical` | 9,866 | 90 | 199 | 11 |

In 177 of the 200 strings the total advance under the defaults differs from the total under
`-kern,-liga,-clig`, so kerning and ligatures are exercised. For example, `AV` is 2,600 font units wide by default and 2,708
without kerning, and `office` shapes to four glyphs (the `ffi` ligature is glyph 76) by default and
to six without ligatures. Under `vertical`, every glyph gets a nonzero offset derived from its
extents and the face's ascender and descender (for `A`: x offset -677, y offset -1916, y advance
-2400), so the extents path does run.

## Results

All variants of all runs produced the same stream, SHA-256
`fe7d9b489827b2af8a04625f50754c7bafcac65fe4aeb58795a1cfc1f8e748b4`, and no `mismatch` line.

| Run | Host | Target | Toolchain | Variants |
| --- | --- | --- | --- | --- |
| local, commit `ec5f0c2` | macOS (Darwin 25.6.0), Apple M5 | aarch64-apple-darwin | rustc 1.100.0 (Homebrew), LLVM 23.1.6 | native release, native release `-C target-cpu=native`, native debug |
| CI run 45112351770, commit `ec5f0c2` | GitHub Actions `ubuntu-latest` (Linux 7.0.0-1020-azure), AMD EPYC 9V74 | x86_64-unknown-linux-gnu | rustc 1.96.0, LLVM 22.1.2 | native release, native release `-C target-cpu=native`, native debug |
| the same run | the same runner, Node 22.23.5 (V8 12.4.254.21) | wasm32-unknown-unknown | rustc 1.96.0 | wasm32 release, wasm32 release `+simd128` |
| the same run | the same runner, headless Chromium 157.0.8103.78 through Playwright | wasm32-unknown-unknown | rustc 1.96.0 | wasm32 release |

The Mac and the CI runner used different compilers (1.100.0 with LLVM 23 on the Mac, 1.96.0 with
LLVM 22 in CI) and still agreed.

The wasm32 build could not run on the Mac: Homebrew's rustc ships no wasm32 standard library and no
`rust-lld`, and installing either was out of scope. So every wasm32 result comes from the CI
runner.

## Source review: float use

`rustybuzz` 0.20.1 depends on `ttf-parser` 0.25.1 and on `core_maths` 0.1.1, which routes float
functions to the pure-Rust `libm` 0.2.16 instead of `std`. The shaping output is integers in font
units; the question is whether a float sits on the way to them. These are all the `f32` sites in
`rustybuzz/src`, and whether a static TrueType face like Lato reaches them:

| Site | What | Reached for Lato |
| --- | --- | --- |
| `hb/ot_layout_gpos_table.rs` (`Device::Variation`) | variation delta, rounded through `libm` | No: needs variation coordinates and a `GDEF` variation store |
| `hb/face.rs` `glyph_extents` (PNG branch) | scales a bitmap glyph's extents | No: Lato has no `sbix` or `CBDT` |
| `hb/face.rs` `glyph_extents` (`COLR` branch) and `hb/paint_extents.rs` | color glyph extents | No: Lato has no `COLR` |
| `hb/aat_layout_trak_table.rs` | AAT tracking | No: Lato has no `trak` |
| `hb/common.rs` and `hb/text_parser.rs` | parsing a `Variation` string such as `wght=500` | No: no variations are set |
| `hb/shape_wasm.rs` | the `wasm-shaper` feature | No: the feature is off |
| `hb/ot_layout_gsubgpos.rs:957` | `(max(4, len) as f32 * 1.5) as usize` when nested contextual lookups grow a buffer | Possibly. It sets a capacity, not an output value, and for lengths this small the conversions are exact |

`glyph_extents` for a `glyf` face reads the glyph's integer bounding box from the `glyf` header
(`ttf-parser` `Glyf::bbox`), not from the outline, so vertical text stays integer too. In
`ttf-parser`, the tables that Latin shaping reads (`cmap`, `hmtx`, `hhea`, `GSUB`, `GPOS`, `head`,
`OS/2`, `maxp`, `loca`) contain no `f32`. Floats appear only in outline building, variation
tables and CFF.

So for this face and these features the Latin shaping path does no float arithmetic that can
reach an output value. With a variable font or a color font, it would.

## Limits

- **One face.** Only Lato Regular is pinned in the repository. Lato Bold or Italic, other families,
  CFF fonts and variable fonts were not tested.
- **Latin only**, as the card's aperture says. Arabic, Indic, Hangul and the other complex shapers
  were not exercised, apart from what forced right-to-left Latin reaches.
- **No hinting.** No pixels-per-em was set, so `GPOS` device-table hinting deltas were not applied.
  Lato has no `GDEF`, so they could not have been anyway.
- **Hosts.** One Apple M5 and one AMD EPYC runner. No Intel x86-64, no 32-bit ARM, no Windows,
  and only the V8 engine (Node and Chromium both use V8). Firefox and Safari were not tested.
- **Flags.** `-C target-cpu=native` and `+simd128` were tested. Fast-math style flags were not.
- **Versions.** `rustybuzz =0.20.1` with `ttf-parser` 0.25.1, pinned in the experiment's
  `Cargo.toml` and `Cargo.lock`. An update can change the answer.

## Input to #142

The card lists three outcomes: "identical, with no float use in the Latin path: use `rustybuzz`,
pinned, with a cross-target gate"; "identical, with float use: use it pinned, with a gate on every
update"; and "different: keep advance-only layout". This experiment found the first: identical output
on the hosts and inputs above, and no float arithmetic in the Latin path for Lato Regular. It
leaves #142 three facts to weigh:

1. "No float use" holds for a static TrueType face without color or bitmap glyphs. A variable
   font, a color font or a bitmap font would reach the `f32` sites in the table above.
2. Only one face of one family was tested, and no complex script.
3. The one `f32` site that may run (`ot_layout_gsubgpos.rs:957`) sizes a buffer and does not
   reach an output value.

The harness in `research/rustybuzz-wasm32/` can serve as the cross-target gate the first outcome
asks for, or as a model for it.
